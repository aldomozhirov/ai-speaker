# Phases 6–7 — Session robustness & Spotify ducking

> Implementation plan. Companion to `IMPLEMENTATIONPLAN.md` §6–§7.
> Current state: Phases 1–5 done. Phase 5 ships half-duplex (mic muted while the bot
> speaks) because the XVF3800's residual echo measured louder than the user's voice at
> the mic; voice barge-in is disabled behind `VOICE_HALF_DUPLEX=0`.

## 0. Findings from investigating the current box

These change the shape of the work. Established by reading the installed pipecat
source and the live system, not assumed.

| # | Finding | Consequence |
|---|---|---|
| 1 | **Spotify on this box is `spotifyd`, not raspotify/librespot.** `~/.local/bin/spotifyd` under user unit `spotifyd.service`, `backend = "pulseaudio"`, `volume_controller = "none"`. Raspotify is only a leftover apt source; nothing is installed. | Phase 7's duck target is spotifyd's PipeWire stream node. The plan doc's "librespot stream node" wording is stale. |
| 2 | **Context-window compression is off.** `voice_agent.py` never sets `context_window_compression`; pipecat defaults it to `None`, and `_connect()` only adds the config `if cwc and cwc.enabled`. | The 15-min audio-session limit and the 128k context window currently apply hard. This is the single biggest Phase 6 gap and it is a two-line fix. |
| 3 | **Session resumption is already on.** `_connect()` unconditionally sends `SessionResumptionConfig(handle=...)`, and `_handle_msg_resumption_update` stores every `new_handle`. `_reconnect()` replays it. | No work needed; verify the handle actually arrives in logs. |
| 4 | **There is no `GoAway` handling.** `grep -i go_away llm.py` → nothing. Reconnection is purely reactive: the websocket closes, `session.receive()` raises, `_handle_connection_error` → `_reconnect()`. | The ~60 s advance warning is unused, so every ~10 min connection rollover costs a short audible gap. Measure it before deciding whether to care. |
| 5 | **The Phase 5 `LLMRunFrame` gotcha does not recur on reconnect.** `_disconnect()` clears `_ready_for_realtime_input`, but `_handle_session_ready()` sets it back to `True` on the resumption-handle path, and `_create_initial_response(for_reconnect=True)` sets it on the re-seed path. | Good news — but it is exactly the failure mode to watch for in the soak test (symptom: bot goes permanently deaf ~10 min in). |
| 6 | **The half-duplex gate can deadlock on reconnect.** `AudioGate.mute()` has no timeout; it is only released by `BotStoppedSpeakingFrame`. If the connection drops mid-utterance that frame may never arrive. | Real bug, must fix in Phase 6. |
| 7 | **`volume_sync.py` drives `@DEFAULT_AUDIO_SINK@`, never individual streams.** | Stream-level ducking will not fight the MPRIS/Spotify-Connect volume bridge. Confirms the plan doc's approach is safe here. |
| 8 | **The AEC reference is tapped at the aloop sink's *monitor*** (`20-xvf-aec-ref.conf`), i.e. downstream of per-stream volume. | Ducking a stream also ducks it in the AEC reference, automatically and consistently. Ducking must stay upstream of that monitor — which stream-level ducking is. |
| 9 | **Music will trip the session's Silero VAD.** `LLMUserAggregatorParams(vad_analyzer=SileroVADAnalyzer())` runs on the mic; music at listening volume is speech-like enough to produce false turn boundaries. | Argues for ducking the *whole session*, not per-bot-utterance. See decision D1. |
| 10 | **A crash leaves CamillaDSP on `voice.yml`.** `DspProfileSwitcher._previous_path` is in-memory only; `Restart=on-failure` brings the daemon back with no idea what to restore. | Phase 6 robustness item. |

## Phase 6 — Session robustness

Goal per the plan doc: *a deliberate >20 minute continuous conversation survives
without going silent or losing context.* Do this before any tool-calling work.

### 6.1 Enable context-window compression *(the actual fix)*

`voice_agent.py`, in the `GeminiLiveLLMService.Settings(...)` block:

```python
from pipecat.services.google.gemini_live.llm import ContextWindowCompressionParams
...
    context_window_compression=ContextWindowCompressionParams(
        enabled=VOICE_CONTEXT_COMPRESSION,
        trigger_tokens=VOICE_COMPRESSION_TRIGGER_TOKENS,  # None = 80% of window
    ),
```

New env vars on `voice-agent.service`: `VOICE_CONTEXT_COMPRESSION=1`,
`VOICE_COMPRESSION_TRIGGER_TOKENS` (unset → pipecat's default). Leave the flag
switchable so it can be A/B'd against the 15-min limit rather than assumed to work.

### 6.2 Bound the mute gate (finding #6)

`pw_transport.py` — give `AudioGate.mute()` a hard ceiling:

```python
def mute(self, max_seconds: float = 30.0) -> None:
    with self._lock:
        self._muted = True
        self._mute_deadline = time.monotonic() + max_seconds
```

and have `muted()` fall open past the deadline, logging once when it does. A bot turn
never legitimately runs 30 s; if the gate is still shut at that point, a frame was
lost and a deaf assistant is strictly worse than an echoey one. Env: `VOICE_MAX_MUTE_SECONDS=30`.

### 6.3 Watch for errors and reconnects in the pipeline

`SessionMonitor` currently observes only bot-speaking and transcription frames. Add:

- `ErrorFrame` → log, LED `error`. Pipecat's `push_error` fires this after
  `MAX_CONSECUTIVE_FAILURES = 3` (with the counter reset after
  `CONNECTION_ESTABLISHED_THRESHOLD = 10.0` s of stability), i.e. it means the session
  is genuinely dead. Close the session rather than sitting silent.
- Reconnect visibility: pipecat logs `"Connecting to Gemini service with
  session_resumption_handle: ..."` at INFO. That string is the soak test's primary
  evidence; no code needed, just know to grep for it.

### 6.4 Absolute session cap + crash-safe DSP restore (finding #10)

- `VOICE_MAX_SESSION_SECONDS` (default `1800`): a watchdog that calls
  `task.stop_when_done()`. Prevents a wedged session from holding the voice profile and
  the mic indefinitely. This is a safety net, *not* the 15-min API limit — 6.1 handles that.
- Persist `DspProfileSwitcher._previous_path` to `$XDG_RUNTIME_DIR/voice-agent-dsp.json`
  when switching to voice, delete it on successful restore. On daemon startup, if the
  file exists (or CamillaDSP's current config path is `voice.yml`), restore and clear it.
  Runtime dir, not `~/.config` — a reboot legitimately resets this.

### 6.5 Soak test harness

The 8 s idle timeout means a 20-minute conversation cannot happen by accident. Test with
a temporary drop-in rather than editing the unit:

```
systemctl --user edit voice-agent.service   # Environment=VOICE_IDLE_SECONDS=3600
```

Speak every minute or two for 25+ minutes, then revert the drop-in. Watch:

```
systemctl --user status voice-agent.service -l -n 200 --no-pager
```

## Phase 7 — Ducking

### 7.1 Resolve the spotifyd stream node by name

New `~/.local/bin/duck.py` (imported by `voice_agent.py`). Resolution via `pw-dump`,
selecting nodes where `info.props["media.class"] == "Stream/Output/Audio"` and
`application.name` / `application.process.binary` matches `VOICE_DUCK_MATCH`
(default `spotifyd`). Never cache the ID across sessions — the stream is destroyed and
recreated on every track-session change. Returns a list, so a second player later
(Bluetooth, AirPlay) is a config change, not a code change.

Use `wpctl get-volume <id>` / `wpctl set-volume <id> <v>` via subprocess, matching
`volume_sync.py`'s existing convention (`WPCTL_PATH`, default `/usr/bin/wpctl`) rather
than adding `pulsectl` to the voice-agent venv.

### 7.2 Duck and restore

- Record each matched stream's pre-duck volume, set to `VOICE_DUCK_LEVEL` (default `0.20`).
- **Ramp** over `VOICE_DUCK_RAMP_MS` (default `200`) in ~8 steps. A single
  `wpctl set-volume` step is an instantaneous gain change and will click.
- On restore, re-resolve: only restore streams that still exist *and* that we ducked.
  If Spotify stopped mid-conversation, restore is a no-op; if it started mid-conversation
  it plays at full volume until the next session, which is acceptable and much simpler
  than watching the graph.
- Nothing playing → resolve returns `[]` → every operation is a no-op. This is the
  common case and must be silent, not an error.

### 7.3 Wire into the session lifecycle

Duck in `VoiceAgent._run_session()` immediately after `send_led_state("listening")`;
restore in the same `finally:` block as `self._dsp.restore()`. Restoring in `finally`
is what makes the button-cancel, closing-phrase, idle-timeout and exception paths all
correct with one piece of code.

### 7.4 Guardrails (non-negotiable, from the plan doc)

- Never duck via CamillaDSP volume — that is global safety headroom for the tweeter.
- Never duck the default sink (node 76) — that is the user's physical volume and
  `volume_sync.py`'s exclusive domain (finding #7).
- Stream-level only.

## Open decisions

**D1 — Duck for the whole session, or only while the bot speaks?**
The plan doc says bot-started/stopped-speaking. **Recommendation: whole session.**
Two reasons: per-utterance ducking pumps the music several times per exchange, and
finding #9 means unducked music during the *listening* half will trip Silero VAD and
manufacture false turns. If a deeper duck while the bot actually speaks turns out to be
wanted, that is an easy second level on top.

**D2 — Duck depth.** Starting at `0.20`. Worth tuning against the wake-word detector
once ducking exists, since ducked music is also the condition under which Phase 3's
"< 1 false accept/hour" needs to keep holding.

**D3 — Barge-in re-test.** *(corrected 2026-08-22)* An earlier version of this note
claimed ducking would help barge-in. That is mostly wrong and worth stating plainly:
ducking lowers **spotifyd's** stream, but the echo that broke full duplex is the
**assistant's own voice**, which ducking does not touch. Ducking only helps in the
narrower case where music is playing and adds broadband echo the AEC must also cancel.

The lever that actually moves the ratio is `VOICE_OUTPUT_GAIN` (added 2026-08-22):
the AEC residual scales with how loud the bot plays, while the user's voice at the mic
does not. Measured baseline was ~600 residual vs ~400–600 for the user's voice, so
halving the bot's level should put the residual clearly underneath. The cost is an
assistant that is quieter to listen to — which is the real trade-off to judge, not
whether the mechanism works.

Test rig lives in `~/.config/systemd/user/voice-agent.service.d/50-bargein-test.conf`
(`VOICE_HALF_DUPLEX=0`, `VOICE_OUTPUT_GAIN=0.5`). Delete it + `daemon-reload` +
restart to return to the known-good half-duplex config. If barge-in still misfires at
0.5, the remaining lever is the deferred §1.2 `target.delay.sec` calibration — a
theoretical 0.341 s estimate that has never been measured, and the likeliest reason
the AEC needs ~500 ms to converge and tops out at ~35 dB.
