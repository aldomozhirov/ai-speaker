Concrete implementation plan for "hey jarvis, play Bohemian Rhapsody".
Carries over the design sketched in the earlier session (Web API OAuth,
search → play, device resolved by name) and adds what was verified on the
live device on 2026-08-22.

## What was already decided (earlier session)

- Tool name/shape: `spotify_play_track(query)`.
- Mechanism: `GET /v1/search?type=track` → `PUT /v1/me/player/play` with a
  `device_id` resolved by matching spotifyd's `device_name` ("AI Speaker"),
  never hardcoded.
- Auth: Authorization Code flow, redirect URI `http://127.0.0.1:8888/callback`,
  scopes `user-modify-playback-state` + `user-read-playback-state`, refresh
  token stored locally under `~/.config/ai-speaker/`.
- Blocking prerequisite: a Spotify Developer app has to be registered
  (the user confirmed none exists yet).

## Design

### Files

| Path | Change |
|---|---|
| `~/.local/bin/spotify_web.py` | **new.** Token manager + search + device resolution + play. No pipecat imports, so it doubles as a CLI (`auth`, `devices`, `search`, `play`) for testing without the voice pipeline. `aiohttp` imported lazily inside the async paths so the `auth` subcommand runs under `/usr/bin/python3` |
| `~/.config/ai-speaker/spotify.json` | **new**, mode 0600. `{client_id, client_secret, refresh_token}` |
| `~/.local/bin/spotify_tools.py` | add `spotify_play_track` wrapping `spotify_web`, same `mark_quick_action()` + `result_callback` shape as the existing four |
| `~/.local/bin/voice_agent.py` | import the tool, add to the `LLMContext(tools=[…])` list, extend `VOICE_SYSTEM_PROMPT` with one clause about playing a requested song |
| `WAKE_WORD_GEMINI_INTEGRATION.md` | rewrite §8.3 from "not started" to what shipped, incl. the MPRIS-registration finding |

Credentials live in their own JSON rather than an `EnvironmentFile` because
the refresh token can be rotated at runtime and systemd only reads env files
at unit start. Static tuning (`SPOTIFY_DEVICE_NAME`, `SPOTIFY_MARKET`,
`SPOTIFY_HTTP_TIMEOUT`) stays as `Environment=` lines in the unit, matching
how the other phases are configured.

### `spotify_web.py`

```python
TOKEN_URL  = "https://accounts.spotify.com/api/token"
API        = "https://api.spotify.com/v1"
DEVICE_NAME = os.environ.get("SPOTIFY_DEVICE_NAME", "AI Speaker")   # spotifyd.conf
TIMEOUT     = float(os.environ.get("SPOTIFY_HTTP_TIMEOUT", "4.0"))

async def _access_token() -> str:
    # in-memory cache, refreshed ~60s before expiry;
    # POST grant_type=refresh_token with HTTP Basic client_id:client_secret.
    # If the response carries a new refresh_token, persist it back to
    # spotify.json atomically (tmp + os.replace, 0600) -- Spotify rotates it
    # for some flows and dropping the new one bricks auth silently.

async def search(query, kind="track", limit=5) -> dict | None:
    # GET /search?q=…&type=kind&limit=…&market=from_token

async def resolve_device() -> str | None:
    # GET /me/player/devices -> exact-match name == DEVICE_NAME (case-folded),
    # cached in memory, re-resolved whenever a play call 404s (spotifyd restart)

async def play(uri, device_id) -> None:
    # PUT /me/player/play?device_id=…
    #   track  -> {"uris": [uri]}
    #   album/artist/playlist -> {"context_uri": uri}
```

`search()` and `resolve_device()` are issued concurrently with
`asyncio.gather`, so a cold "play X" costs two round trips (~0.4-0.6 s from
EE), not three.

### `spotify_play_track`

```python
async def spotify_play_track(
    params: FunctionCallParams, query: str, kind: str = "track"
) -> None:
    """Search Spotify and play the best match on this speaker.

    Args:
        query: What to play, as the user said it (e.g. "bohemian rhapsody",
            "the new Radiohead album").
        kind: One of "track", "album", "artist", "playlist". Use "track"
            unless the user clearly asked for something else.
    """
```

Returns `{"status": "playing", "track": "...", "artist": "..."}` so the model
can confirm what it actually started, and calls
`session_signal.mark_quick_action()` on success — same one-shot behaviour as
the other transport tools, so the mic doesn't reopen over the music that just
started.

Error contract (all `{"status": "error", "error": "<human sentence>"}`, the
model reads them aloud):

| Condition | Message |
|---|---|
| no `spotify.json` / no refresh token | "Spotify isn't linked to this speaker yet." |
| refresh fails 400 `invalid_grant` | "The Spotify link has expired and needs re-authorising." |
| device name not in `/me/player/devices` | "This speaker isn't showing up in Spotify right now." |
| empty search results | "I couldn't find anything called …" |
| 403 | "Spotify says that needs a Premium account." |
| 429 | one retry honouring `Retry-After` if it's ≤ 2 s, else give up |

**Deliberate non-behaviour:** when the speaker isn't in the device list, the
call fails rather than falling back to a `device_id`-less play — that would
start music on whatever the user last used, e.g. their phone in another room.

## Setup steps (user-facing, one-time)

1. **Register the app** at developer.spotify.com/dashboard, using the *same
   Spotify account spotifyd is logged in as* (`31cgpioucyi3uailvoacbgq4ta5i`)
   — a different account's token will not see "AI Speaker" in its device
   list. Enable the **Web API**, add redirect URI
   `http://127.0.0.1:8888/callback` (loopback HTTP is explicitly allowed;
   `localhost` is explicitly *not*). Development mode is fine: the owning
   account is allowlisted automatically.
2. Write client id/secret into `~/.config/ai-speaker/spotify.json` (0600).
3. `python3 ~/.local/bin/spotify_web.py auth` — prints the authorize URL and
   listens on 127.0.0.1:8888. Two ways to complete it on a headless Pi:
   `ssh -L 8888:127.0.0.1:8888 …` and open the URL in the laptop browser, or
   open it anywhere and paste the full `127.0.0.1:8888/callback?code=…` URL
   back into the prompt (the same paste-the-URL trick `spotifyd authenticate`
   uses). Stores the refresh token; run once, survives reboots.

## Known gap this exposes (separate, optional 8.4)

`spotify_play`/`pause`/`next`/`previous` shell out to `playerctl`, and MPRIS
is absent until a Connect client has connected — so from cold, "hey jarvis,
next track" answers "no active media player" today. Once a user token exists
this is a ~30-line fix: on `playerctl` failure, fall back to
`PUT/POST /me/player/{play,pause,next,previous}?device_id=…`. Worth doing
right after 8.3, but it is not required by it.

## Risks

- **Wrong-account app registration** is the most likely way this silently
  half-works: search succeeds, device list is empty. Check 1 catches it.
- **Refresh-token rotation** — handled by persisting any new token; if this is
  missed the failure appears days later as `invalid_grant`.
- **spotifyd restart mid-session** invalidates a cached device id → re-resolve
  on 404 rather than caching for the process lifetime.
- **Music starts at full volume mid-session** while the session's duck is
  still applied to older streams. New streams aren't ducked and aren't
  restored, so nothing gets stuck — but check 5 exists to confirm that
  reasoning against `duck.py` in practice. (Separately confirmed while
  testing: `duck.py`'s `spotifyd|librespot` pattern does match the real
  stream — via `application.process.binary`, since spotifyd leaves
  `application.name` empty — closing an item Step 7 had left unverified.)
